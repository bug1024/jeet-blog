# Bug1024 博客文章写作与摄影规范

## 1. 内容定位

博客用于建立 Bug1024 的长期个人品牌，主要记录：

- 工作中的系统、协作、组织与人的判断；
- 生活中的选择、时间、家庭与个人变化；
- 少量来自真实实践、值得长期保留的技术内容。

文章从具体经历或问题出发。表达应具体、克制、有判断，不追逐热点，不把尚未消化的观点包装成答案，也不为了显得深刻而制造深刻。

默认是单向对外输出。不要在结尾机械地邀请读者留言、联系、讨论或产生共鸣；只有文章本身确实需要提问时，才保留问题。

## 2. 文案语气

### 应该

- 先写事实和经历，再给出判断；
- 区分事实、推测和个人感受；
- 使用自然、准确的现代汉语；
- 保留暂时没有结论的问题；
- 标题清楚表达文章讨论的对象。

### 避免

- 空泛格言和刻意提炼的“金句”；
- “保持热爱”“寻找答案”“与时间和解”等泛化表达；
- 把普通经历包装成宏大叙事；
- 没有内容作用的文学修饰；
- 默认使用“欢迎交流”“如果你也……”“希望与你产生共鸣”等社交型结尾；
- 为凑更新频率而写作。

文学感应来自具体观察、准确节奏和真实细节；文化感应来自视野和判断，而不是古典词语或故作深沉。

## 3. Bug1024 的文风

这里的“像作者”不是模仿早年日记里的旧文腔，也不是给文章统一套上一组常用词。需要保留的是作者观察和思考事情的方式。

### 3.1 从亲历开始

工作、技术和生活文章优先回答以下问题：

- 事情发生在什么背景下；
- 当时实际做了什么；
- 哪个现象改变了原来的判断；
- 现在怎样看，仍有哪些部分没有想清楚。

没有亲历材料时，不得代替作者虚构经历、感受、动机或顿悟。AI 可以查漏、整理和改写，不能补造第一人称事实。

### 3.2 保留思考发生的顺序

作者常用“当时—后来—现在回头看”的时间关系复盘一件事。文章可以保留试错、绕路和判断变化，不必假装项目从一开始就有完整蓝图。

先写清楚为什么做出某个选择，再解释选择背后的机制。不要把后来形成的认识倒灌成最初就存在的目标。

### 3.3 判断要比材料更窄

只对材料能够支撑的范围下结论。一次项目经历可以说明“我在这次实践中发现什么”，通常不足以直接说明“行业正在怎样”“人类将会怎样”或“AI 的未来是什么”。

作者的判断可以明确，但要写出适用条件、现实限制和仍未验证的部分。允许使用“我目前更倾向于”“至少在这个项目里”“现在还不能确定”等表述，但不要每段都加免责声明。

### 3.4 使用朴素而准确的语言

优先使用“做、改、删、保留、发现、遇到、决定、没有完成”等具体动词。能够用“是”“有”直接说明的，不绕成“承担……角色”“形成……机制”“实现……转变”。

可以有文学感，但应来自风、雨、房间、城市、声音、时间等真实可见的细节。可以有幽默，但更适合轻微的自嘲和冷幽默，例如“正经人谁写日记”，不专门解释笑点。

“不是 A，而是 B”并非禁用。只有当它确实修正了一个可能的误解时才使用，同一篇文章不要反复用它制造结论感。

### 3.5 保留人的不整齐

段落长短可以不同。重要的技术细节可以多写，次要过渡可以一句带过；某个问题没有答案，就停在没有答案的位置。不要为了形式完整，强行让每一节都有相同的开头、三条分论点和一段升华。

### 3.6 中文句读与段落节奏

标点首先划分意思，其次才调节节奏。不能为了让句子显得有力，频繁插入句号、冒号或破折号。

#### 句号

一句话已经完成相对独立的意思，或者下一句更换了主语、时间、视角和讨论重点，才使用句号。

不要把铺垫和它所引出的内容强行拆开：

```text
不自然：我做 Soul-TTY 的起因很偶然。有一天看到一篇语音模型的文章，我想试试它的效果。
自然：我做 Soul-TTY 的起因很偶然，最开始只是有一天看到一篇语音模型的文章，想试试它的效果。
```

短句可以用于记录突然发生的事、直接判断、对话或确实需要的停顿，但不连续排列，也不把普通过渡句单独成句。像“问题很快出现了。”“事情没有这么简单。”“后来一切都变了。”这类句子，如果后文才包含实际信息，通常应与后文合并或直接删除。

#### 逗号

同一主语下连续发生的动作、同一层意思中的原因与结果，以及关系紧密的补充说明，可以用逗号连接。Bug1024 的文章允许适当保留长句，不必把每个分句都切成短句。

长句也不能无限延伸。如果一句话中连续更换多次主语，或者同时解释背景、动作、结果和评价，应在意思完成处用句号拆开，而不是用逗号把全部内容串在一起。

#### 冒号

冒号只用于明确的引语、列举、字段说明，或后文确实在解释前文的情况。例如“当前有两条链路：实时对话和异步分析”可以使用冒号。

不要用冒号制造思考和转折：

```text
不自然：我后来意识到一个问题：角色不能只依赖 Prompt。
自然：实际聊了一段时间后，我发现角色很容易回到通用助手的语气，于是才把状态从 Prompt 里拆出来。
```

“我想到一点：”“真正的问题是：”“原因很简单：”“这意味着：”后面如果只是普通陈述，优先改写成一个完整句子。

#### 分号

分号只用于内部已经包含逗号、彼此又明确并列的复杂分句。普通枚举直接使用顿号、逗号或自然叙述，不写成“需要记忆；需要情绪；需要关系”。一段正文通常不需要多个分号。

#### 破折号、括号与问号

- 破折号只表示插入、补充或语意突然转折，不用它包装金句，不用“技术——是人的延伸”制造腔调；
- 括号只放不影响主句成立的次要信息，重要限制应写进正文；
- 问号只保留作者当时确实提出、文章也确实要处理的问题，不用连续设问带动段落；
- 中文正文使用全角中文标点，代码、命令、URL 和英文原文除外。

#### 段落

换段表示叙述对象、时间、论证步骤或阅读重心发生变化，不把每一两句话机械拆成一个段落。相邻短段如果共同说明一件事，应合并；技术细节较多的段落则可以适当拆开，避免一个段落同时承担过多任务。

## 4. 去 AI 味的硬性规则

“自然流畅”不是最终标准。过度顺滑、过度完整和处处正确，往往正是 AI 痕迹的来源。初稿完成后必须单独进行一次去 AI 味修改。

### 4.1 删除没有新增事实的句子

以下内容如果没有带来新的事实、例子或限定，应直接删除：

- “值得注意的是”“需要指出的是”“不可忽视的是”；
- “从某种意义上说”“这背后反映的是”“这也让我重新理解了”；
- 只负责承上启下、删掉后不影响意思的段落；
- 把上一段换一种说法再总结一次的句子。

判断方法：删掉一段后，如果事实、推理和语气都没有损失，这一段就不该保留。

### 4.2 禁止批量制造金句

避免为了适合引用而单独成段的短句，尤其是抽象名词之间的对仗，例如：

```text
技术解决效率，文学保存温度。
模型提供大脑，记忆决定灵魂。
不是回到过去，而是走向未来。
```

偶尔出现一句简短判断没有问题，但它必须由前文自然得出，不能成为文章的固定节拍。

### 4.3 打破模板结构

- 不默认使用“提出问题—三点分析—总结升华”；
- 不把每个概念都拆成同级小标题，再逐一定义；
- 不为了整齐凑出三项、五项或成排的同长度段落；
- 不机械使用“首先、其次、再次、最后”；
- 短文章不强行增加“挑战”“未来展望”“结语”。

结构应从材料中长出来。项目本来是按时间演化的，就按时间写；问题本来集中在两个难点，就只写两个。

### 4.4 降低抽象词和 AI 高频词密度

谨慎使用以下词语：

- 本质、核心、真正、重要的是、关键在于；
- 赋能、生态、维度、范式、闭环、演进、重塑；
- 不仅……更……、从……到……、既……又……；
- 标志着、体现了、彰显了、承载了；
- 在 AI 时代、在快速变化的世界中、面向未来。

这些词不是一律禁止，但出现时必须能够指出具体对象。能写“我把记忆评估移到异步队列”时，不写“完成记忆机制的架构演进”。

### 4.5 不写宣传稿和产品介绍腔

- 不用“强大、创新、无缝、沉浸式、令人惊叹”等形容词替代证据；
- 不按功能清单逐项夸赞项目；
- 不把仍在实验的能力写成已经解决的问题；
- 不用模糊主体，如“业内普遍认为”“研究显示”“不少用户反馈”，除非有可核验来源；
- 不在结尾写“未来可期”“让我们共同期待”等宣传语。

### 4.6 控制排版产生的 AI 感

- 不连续使用大量单句段落；
- 不把普通陈述做成引用块；
- 不滥用粗体、破折号、括号和英文术语；
- 列表只用于确实并列、需要查阅的信息，不用列表代替叙述；
- 小标题表达文章推进到哪里，不使用“核心洞察”“深层意义”“未来探索”等万能标题；
- 文章结尾不重复全文，也不额外拔高主题。

## 5. 写作流程

### 5.1 先建立材料卡

起草前至少确认：

1. 真实背景与时间；
2. 作者亲自做过或看见的事；
3. 一个具体选择、困难或转折；
4. 当时与现在的判断是否不同；
5. 哪些内容仍是推测或尚未完成。

材料不足时先补材料。不能用通顺的常识填满空白。

### 5.2 先写事实稿，再写文章稿

第一遍只整理事实、顺序和技术边界。第二遍再调整节奏、删减重复，并补入作者已经明确表达过的判断。不要在列提纲时先设计金句。

### 5.3 最后单独做人声审阅

逐段检查：

- 这句话是作者提供的事实，还是模型自己补出的合理话；
- 这段是否像作者在复盘，还是像顾问在总结；
- 是否连续出现定义、分类和结论；
- 是否把一个局部经验放大成普遍规律；
- 是否存在读起来正确、删掉也没有损失的句子；
- 是否有一句作者本人在日常表达中不会说的话。

检查后再删除一轮。通常，AI 初稿删掉 10%—20% 会更接近真实写作。

### 5.4 具体改写示例

AI 式表达：

> Prompt 可以描述一种人格，却很难独自维持人格。

Bug1024 式表达：

> 第一版主要依赖 System Prompt。实际聊了一段时间后，我发现它很容易回到通用助手的说话方式，于是才把情绪、关系和记忆拆成独立状态。

AI 式表达：

> 开发过程中最有价值的，是逐渐划清系统边界。

Bug1024 式表达：

> 最后留下来的方案反而简单。主链路只处理正在发生的对话，情绪评估和记忆抽取放到旁路，失败了也不影响这一轮交流。

前者先给抽象结论，后者保留了发生过的事情、修改原因和当前方案。

## 6. 文章结构

结构服务于内容，不强制所有文章套用相同提纲。通常可以包括：

1. 一件具体的事、一个变化或一个问题；
2. 对其背景和机制的解释；
3. 自己形成或修正的判断；
4. 当前结论、行动或仍未解决的部分。

长文章使用二级标题帮助阅读；短文章不为了形式完整强行拆章节。

## 7. Front matter

基础字段：

```yaml
---
title: "文章标题"
description: "用一两句话说明文章具体讨论什么，不写宣传语。"
date: 2026-07-18
author: "Bug1024"
slug: "stable-english-slug"
draft: true
tags:
  - 工作与系统
---
```

规则：

- 文件名：`YYYY-MM-DD-topic.md`；
- `slug`：简短、稳定、无日期，发布后不随意修改；
- `description`：承担文章导语和列表摘要作用，应包含有效信息；
- `tags`：优先复用已有标签，不为细小差异不断创建同义标签；
- 用户未明确要求发布时保留 `draft: true`。

可选视觉关联字段：

```yaml
visual: "bug-visual-001"
```

该字段只用于关联“第 1024 格”视觉作品档案。视觉隐喻与 Prompt 存放在 `data/visuals/<id>.yaml`，不得写入 `alt`。

## 8. 文章标题区的三种模式

### 无摄影题图

默认使用钢蓝文章坐标板。坐标板展示真实的文章序号、日期和阅读时间，不需要在 front matter 中配置。

禁止为了避免无图而添加与正文无关的网络图片、生成图或旧站装饰图。

### “第 1024 格”生成封面

只有图像能够具体解释文章，而不是单纯填补空白时才使用。生成和接入过程必须遵循 `skills/blog-cover-generator/SKILL.md`。

每张正式采用的 AI 生成封面必须：

- 使用连续的 `bug-visual-NNN` 编号；
- 在 `data/visuals/` 中建立独立档案；
- 在文章顶层 front matter 中通过 `visual` 关联档案；
- 保留客观 `alt`，将自然秩序、Bug、钢蓝作用、隐喻和最终 Prompt 写入档案；
- 与图片文件、文章配置一起纳入 Git 管理。

### 有摄影题图

只有当照片与文章存在真实关系时使用：

- 拍摄于文章发生的地点或时期；
- 与文章讨论的空间、时间或具体观察有关；
- 照片促成了文章；
- 照片补充了文字无法表达的信息。

摄影图不是通用封面装修。照片来自作者本人时，优先保留真实的地点、时间和构图意图。

预留的 front matter 合约：

```yaml
cover:
  image: "/images/article/example.jpg"
  alt: "客观说明照片中可见的内容"
  caption: "南京 · 2026 年 4 月"
  position: "50% 40%"
  fit: "cover"
```

字段含义：

- `image`：站内图片路径；
- `alt`：无障碍与搜索使用的客观画面描述；
- `caption`：地点、时间或一句具体观察；
- `position`：裁切焦点，默认 `center`；
- `fit`：默认 `cover`，必须完整保留构图时使用 `contain`。

如果当前模板尚未支持某个字段，Codex 应先说明并补齐模板支持，不能悄悄忽略作者配置。

## 9. 摄影题图尺寸

### 标准画框

| 项目 | 规范 |
| --- | --- |
| 比例 | `4:3` |
| 推荐原图 | `2400 × 1800px` |
| 最低原图 | `1600 × 1200px` |
| 桌面展示 | 约 `328 × 246px` |
| 移动展示 | 内容容器宽度 `100%`，保持 `4:3` |
| 色彩空间 | `sRGB` |
| 默认适配 | `object-fit: cover` |
| 完整构图 | `object-fit: contain` + 低对比度雾灰画框 |

统一的是画框、基线和页面节奏，不是强迫每张照片采用同一种裁切。

### 图片输出

推荐由 Hugo 生成响应式宽度：

- `640w`
- `960w`
- `1440w`
- `1920w`

优先输出 WebP，并保留兼容格式。建议体积：

- 桌面加载版本 `150–300KB`；
- 移动加载版本 `80–160KB`。

不得直接让网页加载相机原始大图。

### 横图、方图与竖图

- 横图：默认进入 `4:3` 页头画框；
- 方图：根据边缘是否重要选择轻微裁切或 `contain`；
- 竖图：默认进入正文，不强行裁成页头横图。必要时另行设计竖图布局。

## 10. 构图与裁切

默认使用 `fit: cover`，但必须检查裁切结果。照片主体不在中心时，通过 `position` 指定焦点，例如：

```yaml
position: "30% 50%"
position: "70% 35%"
```

如果边缘本身属于构图，不得为了填满画框而破坏照片；改用：

```yaml
fit: "contain"
```

Codex 在处理作者照片时不得擅自：

- 改变照片内容或生成不存在的物体；
- 使用强滤镜、渐变、投影或装饰蒙版；
- 为适配页面而忽略原始构图；
- 把照片当作文字背景并在上面叠加标题。

## 11. Alt 与图注

`alt` 与 `caption` 承担不同职责：

- `alt` 客观说明画面里有什么；
- `caption` 记录地点、时间或拍摄时的具体观察。

推荐图注：

```text
南京 · 2026 年 4 月
```

```text
下午五点，建筑的影子越过窗沿。
```

避免图注：

```text
生活处处是风景。
在光影中寻找答案。
时间留下的痕迹。
```

## 12. 正文图片

- 图片应与上下文存在明确关系；
- 图注紧随图片，不用图片文件名代替说明；
- 不连续堆放多张近似照片；
- 竖图保持合理最大宽度，不放大到模糊；
- 图片可以突破正文窄栏，但不得超出全站内容网格；
- 技术截图优先保证文字可读，不套摄影画框。

## 13. 发布前检查

### 内容

- 标题与正文讨论的是同一件事；
- `description` 有信息量，不是宣传语；
- 结论有事实或经历支撑；
- 已完成独立的去 AI 味修改，不是边生成边自我确认；
- 没有虚构作者的经历、感受、动机和结论；
- 章节结构来自材料，而不是固定模板；
- 已删除重复总结、万能过渡和可有可无的金句；
- 抽象判断没有超过具体材料能够支撑的范围；
- 短句、冒号、分号和破折号没有被用来人为制造节奏；
- 段落按照意思划分，没有连续出现只负责铺垫的单句段；
- 删除可有可无的金句、升华和社交邀请；
- 标签复用了现有体系。

### 摄影

- 照片与文章确实相关；
- 已检查桌面和移动裁切；
- `alt`、`caption`、`position`、`fit` 正确；
- 图片尺寸和体积合适；
- 竖图没有被强行裁成横图。
